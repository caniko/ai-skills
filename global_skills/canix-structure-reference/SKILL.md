# Canix Structure Reference

## Role

This is a shared reference, not a standalone workflow. Load it from canix,
workspace, release, preflight, Plinth, or Simit skills whenever a task crosses
repository boundaries. Keep specialized skills focused on their own procedure;
do not duplicate these ownership and path facts.

## Canonical roots

| Area | Canonical location | Owner / purpose |
|---|---|---|
| canix repository | `/data/nvme0/can/canix` | NixOS/Home Manager configuration, Rust CLI, secrets, and fleet policy |
| project workspace | `/data/nvme0/can/canix/projects` | Canix-owned project checkouts, forks, worktrees, personal material, and archives |
| workspace catalog | `projects/{owned,forks,upstream,worktrees,...}` | Runtime-discovered project identity and checkout paths |
| observed state | canix workspace scanner output | Git revisions and working-tree state |
| mutable state | `/data/nvme0/can/ProjectState` | Build, cache, dataset, generated, and runtime state outside project source |

Within the canix repository, the durable source layout is:

- `flake/` — flake-level modules, configurations, formatters, checks, and shells;
- `root/hosts/<host>/` — host-specific NixOS configuration;
- `root/modules/` — shared NixOS modules;
- `home/` — Home Manager configuration;
- `age/` — agenix secret declarations and encrypted material;
- `lib/` — pure data, facades, and generated sidecars;
- `cli/` — the operator-facing Rust CLI.

## Ownership boundaries

- Canix owns project selection, checkout paths, lifecycle, and project-aware
  workflows through its runtime workspace scanner and CLI.
- Fleetix owns fleet topology: hosts, links, domains, services, and storage
  facts. Canix consumes its generated topology sidecar through approved facades.
- `lib/generated/*.nix` files are generated consumers. Edit their Pkl or other
  canonical source and run the documented generator; do not hand-edit sidecars.
- Simit owns Simit-managed generator features such as flake, CI, hooks, release
  trust, and packaging. It does not own canix project locations.
- Skillnet owns skill catalogs and materialized views only. It is not a project
  registry; its local TOML is generated by canix Home Manager configuration.
- Project checkouts under `projects/` are canix-managed gitlinks or worktree
  material. Resolve and mutate them through the canix workspace workflow; do
  not infer paths from `~/projects` or clone directly into the workspace root.

## Build-host invariant

Atlas is the sole build host for the fleet. Never perform a native aarch64
build on a target device (including `thething`), and never configure a target
host as a Nix remote builder. Target-host SSH is for inspection and service
verification only. For aarch64 consumers, evaluate and build the Crossbow
configuration from Atlas; if the Atlas-side Crossbow recovery path is needed,
run it on Atlas and keep the target host out of the build graph.

## Resolve and validate

From the canix checkout, use the current admin CLI:

```sh
CANIX_PROJECTS_ROOT=/data/nvme0/can/canix/projects canix workspace check --skip-physical-paths
CANIX_PROJECTS_ROOT=/data/nvme0/can/canix/projects canix workspace check
canix --output json workspace show <project>
canix workspace cleanup
nix flake check --no-update-lock-file
```

The environment override is useful on Atlas while the installed Home Manager
configuration still names the retired `/data/nvme0/can/Projects` root.
Regenerate that configuration from canix's `home/user/shared/skillnet.nix` /
CLI configuration and activate the current generation before dropping the
override. If Skillnet reports the retired root, repair its generated state;
do not add a second project registry.

Workspace state is scanned live. If the installed personal `canix` binary
lacks `workspace`, build/use the current admin CLI from `cli/` instead of
reviving removed workspace scripts.

For project changes, inspect both the canix parent and the affected checkout:

```sh
git -C /data/nvme0/can/canix status --short
git -C /data/nvme0/can/canix/projects/<manifest-relative-path> status --short
```

Keep path changes, manifest updates, gitlink changes, lock refreshes, and
generated-sidecar regeneration as separate, reviewable operations.
