# Lessons

- 2026-05-22: Verify install guidance against both `Cargo.toml` and `git tag --list | sort` before replacing version or tag snippets; planning docs often describe the target state, not the publishable state.
- 2026-05-22: Move durable rules into stable topic pages close to where readers need them, and delete phase sequencing, branch naming, and model-routing instructions instead of paraphrasing them.
- 2026-05-22: For mdBook repos that commit generated output, rebuild `docs/book` after removing source planning pages and search both `docs/src` and `docs/book` for stale phase/planning text.
- 2026-05-22: If `mdbook` is missing on PATH, check the repo's Nix dev environment before stopping; many docs repos provide the required builder there even when the host shell does not.
- 2026-05-22: If stable docs already claim a planning tree was retired, treat any reintroduced `docs/planning` content as suspect and re-verify the live install or release surface from workflows, manifests, and tags before preserving anything.
- 2026-05-22: Before retiring a plan that may still contain active work, run a dedicated progress review and keep unfinished or blocked items in planning until they are either completed or consolidated into a replacement plan.
- 2026-05-22: When a user explicitly defers deleting old plan files, still fold durable guidance into stable docs and limit stale-reference cleanup to navigation/text that the user put in scope.
- 2026-05-22: If a future roadmap appears under `docs/src/planning` during a final retirement check, move or classify it outside active planning instead of deleting it, then re-run the exact directory assertion.
- 2026-05-24: When retiring one completed plan from a mixed planning tree, keep incomplete sibling plans published and verify stale-reference searches are scoped so retained plans do not mask deleted-plan leftovers.
- 2026-05-24: If the named obsolete plan directory is already absent, verify it is neither tracked nor referenced from published navigation, then update the replacement plan's README to state the retirement instead of running a no-op deletion.
- 2026-05-24: When stable docs exist in both README and mdBook, preserve retired plan guidance in the mdBook too; README-only preservation is not enough if the plan was published from `docs/src/SUMMARY.md`.
- 2026-05-25: When a published plan is only partially complete because external workflow evidence failed, remove it from reader navigation and fold verified durable guidance into stable docs, but keep the plan files for the unresolved follow-up.
- 2026-05-25: When planning files live outside the published docs tree, still run progress review before deletion; completed-but-superseded plans can be removed, while partial cross-repo plans should stay unlinked with stale sibling references cleaned up.
- 2026-05-25: If the user explicitly objects to retained unlinked planning files, delete the execution scaffolding after verifying stable docs and source artifacts already cover the durable behavior; report any stale plan claims instead of preserving them.
- 2026-05-25: When a mixed planning tree includes partial fleet work, removing `SUMMARY.md` exposure can be the correct retirement boundary; keep the source plans for unresolved evidence while stable docs carry shipped behavior.
- 2026-05-25: Before deleting a whole published planning tree, search stable docs for stale snippets copied from the plans; fix those snippets first so generated docs do not preserve old execution paths.
- 2026-05-26: A `clean-shipped` plan set may live entirely as untracked files when the planning work was created in-session and only the implementation commits landed. `git rm -r <plan-dir>` fails with `pathspec did not match`; fall back to `rm -rf <plan-dir>` after confirming `git ls-files <plan-dir>` is empty. Always check tracking state before choosing the removal command.
- 2026-05-26: When a plan-set has companion architecture dossiers under `docs/src/planning/<slug>-research.md` that the caller wants retained, prune only the per-phase listing and Overview link from `SUMMARY.md` but keep the dossier link entries. Rename the section heading from `Plan:` to `Architecture:` so the navigation reflects the post-retirement intent — a "Plan:" heading with no plan files reads as a broken nav.
- 2026-05-27: Measurement-heavy plans accumulate point-in-time sample/cargo/summary logs alongside genuinely durable methodology. In clean-shipped mode, fold the methodology (script, what-to-measure rationale, known result table) into a single stable docs page under the project's existing topic tree (e.g. `docs/src/testing/`); drop the per-run sample logs as observation artifacts of a specific host state, not reproducibility primitives. The reproduction recipe + script + a one-time result table are durable; the raw `build-*-samples.log` files are not.
- 2026-05-27: In `clean-shipped` mode the plan-dir `.calibration.json` sidecar typically carries uncommitted modifications from the just-completed `skillnet calibration verify` write; use `git rm -rf <plan-dir>` (not `-r`) so the sidecar deletion is not refused by `git`.
- 2026-05-27: A per-phase `*-results.md` file that captures an empirical verdict (probe outcome, RED/GREEN call) is durable evidence, not execution scaffolding — it tends to be cited from both the companion design dossier and stable docs. Before `git rm -r <plan-dir>`, grep stable docs and sibling dossiers for links into the plan dir; promote any cited results file up to `docs/src/planning/<slug>-results.md` (sibling of `-design.md`/`-research.md`) and rewrite the references in the same commit. Cheaper to restore proactively than to chase broken links after deletion.
- 2026-05-27: `cd` inside the Bash tool persists the cwd between calls under nu shell, so a follow-up `git status docs/book` or `grep -rn ... docs/book/` after `cd docs && mdbook build` silently resolves against `docs/docs/book/` and reports "No such file or directory" / "nothing to commit". Use absolute paths (or `git -C <abs>`) for validation greps after any `cd`, otherwise the final stale-reference check is a false negative.
- 2026-05-27: When deleting a whole planning tree, search non-book fixtures and diagnostic scripts too; generated verdict mappings often point at old plan phase files and need stable docs anchors before the plan directory can disappear cleanly.

- 2026-05-27: When the same-session caller already moved durable knowledge into `AGENTS.md` and a memory file before clean-shipped retirement, step 4 is a no-op verify (grep AGENTS.md for the schema sections, ls the memory file). Skip rewriting; just confirm. Avoids duplicating durable content into both AGENTS.md and a stable docs page that does not exist for this repo (canix has no mdBook `docs/src/` tree).
- 2026-05-27: When the plan-set's own final phase was the docs-rollup phase (Phase N: rewrite commands.md / write migration page / append CHANGELOG / bump Cargo.toml), step 4 is again a no-op verify in clean-shipped mode — the predecessor execution already migrated everything. Spend the time on a 4-grep audit instead (sync flag table count in commands.md, line count of the new migration page, count of version-anchor matches in option-b.md and CHANGELOG.md) to prove the rollup actually landed before deleting the plan files.
- 2026-05-28: A "Document plan" commit landing as HEAD with the plan-set's own files modified or with an unresolved-findings untracked doc in `docs/src/planning/` is a strong signal the plan is mid-execution, not retirable. Cheap triage: HEAD commit subject + `git status` + `grep -c '^- \[x\]' <phase>.md` across phases. If any acceptance checkboxes are unchecked AND there are uncommitted edits to files the phase touches, bail out of `general` mode without running deeper inventory — the plan should stay published.

### 2026-05-28 — Skillnet parsing chokes on retired-row markers in phase tables

When a multi-phase plan retires a phase mid-stream (e.g. phase 06 retired and replaced by phase 08), do **not** keep a `| 06 | — (retired) | …` row in the README's phase table — skillnet's `calibration init` parser reads the File column as a filesystem path and fails on the em-dash. Drop the row entirely; document the gap in a one-line note above the table instead. The numbering gap is harmless once skillnet can complete its init.

- 2026-05-28: If the requested planning tree is already gone, still search stable docs and bookkeeping for plan-era phrases such as `Phase N` or `this phase`; a no-op deletion can still need cleanup so user-facing docs read as current product behavior.
