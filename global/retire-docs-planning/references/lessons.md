- 2026-05-22: Verify install guidance against both `Cargo.toml` and `git tag --list | sort` before replacing version or tag snippets; planning docs often describe the target state, not the publishable state.
- 2026-05-22: Move durable rules into stable topic pages close to where readers need them, and delete phase sequencing, branch naming, and model-routing instructions instead of paraphrasing them.
- 2026-05-22: For mdBook repos that commit generated output, rebuild `docs/book` after removing source planning pages and search both `docs/src` and `docs/book` for stale phase/planning text.
- 2026-05-22: If `mdbook` is missing on PATH, check the repo's Nix dev environment before stopping; many docs repos provide the required builder there even when the host shell does not.
- 2026-05-22: If stable docs already claim a planning tree was retired, treat any reintroduced `docs/planning` content as suspect and re-verify the live install or release surface from workflows, manifests, and tags before preserving anything.
- 2026-05-22: Before retiring a plan that may still contain active work, run a dedicated progress review and keep unfinished or blocked items in planning until they are either completed or consolidated into a replacement plan.
- 2026-05-22: When a user explicitly defers deleting old plan files, still fold durable guidance into stable docs and limit stale-reference cleanup to navigation/text that the user put in scope.
- 2026-05-22: If a future roadmap appears under `docs/src/planning` during a final retirement check, move or classify it outside active planning instead of deleting it, then re-run the exact directory assertion.
- 2026-05-24: When retiring one completed plan from a mixed planning tree, keep incomplete sibling plans published and verify stale-reference searches are scoped so retained plans do not mask deleted-plan leftovers.
- 2026-05-24: If the named obsolete plan directory is already absent, verify it is neither tracked nor referenced from published navigation, then update the replacement plan's README to state the retirement instead of running a no-op deletion.
- 2026-05-24: When stable docs exist in both README and mdBook, preserve retired plan guidance in the mdBook too; README-only preservation is not enough if the plan was published from `docs/src/SUMMARY.md`.
- 2026-05-25: When a published plan is only partially complete because external workflow evidence failed, remove it from reader navigation and fold verified durable guidance into stable docs, but keep the plan files for the unresolved follow-up.
- 2026-05-25: When planning files live outside the published docs tree, still run progress review before deletion; completed-but-superseded plans can be removed, while partial cross-repo plans should stay unlinked with stale sibling references cleaned up.
- 2026-05-25: If the user explicitly objects to retained unlinked planning files, delete the execution scaffolding after verifying stable docs and source artifacts already cover the durable behavior; report any stale plan claims instead of preserving them.
- 2026-05-25: When a mixed planning tree includes partial fleet work, removing `SUMMARY.md` exposure can be the correct retirement boundary; keep the source plans for unresolved evidence while stable docs carry shipped behavior.
- 2026-05-25: Before deleting a whole published planning tree, search stable docs for stale snippets copied from the plans; fix those snippets first so generated docs do not preserve old execution paths.
- 2026-05-26: A `clean-shipped` plan set may live entirely as untracked files when the planning work was created in-session and only the implementation commits landed. `git rm -r <plan-dir>` fails with `pathspec did not match`; fall back to `rm -rf <plan-dir>` after confirming `git ls-files <plan-dir>` is empty. Always check tracking state before choosing the removal command.
- 2026-05-26: When a plan-set has companion architecture dossiers under `docs/src/planning/<slug>-research.md` that the caller wants retained, prune only the per-phase listing and Overview link from `SUMMARY.md` but keep the dossier link entries. Rename the section heading from `Plan:` to `Architecture:` so the navigation reflects the post-retirement intent — a "Plan:" heading with no plan files reads as a broken nav.
- 2026-05-27: Measurement-heavy plans accumulate point-in-time sample/cargo/summary logs alongside genuinely durable methodology. In clean-shipped mode, fold the methodology (script, what-to-measure rationale, known result table) into a single stable docs page under the project's existing topic tree (e.g. `docs/src/testing/`); drop the per-run sample logs as observation artifacts of a specific host state, not reproducibility primitives. The reproduction recipe + script + a one-time result table are durable; the raw `build-*-samples.log` files are not.
- 2026-05-27: In `clean-shipped` mode the plan-dir `.calibration.json` sidecar typically carries uncommitted modifications from the just-completed `skillnet calibration verify` write; use `git rm -rf <plan-dir>` (not `-r`) so the sidecar deletion is not refused by `git`.
- 2026-05-27: A per-phase `*-results.md` file that captures an empirical verdict (probe outcome, RED/GREEN call) is durable evidence, not execution scaffolding — it tends to be cited from both the companion design dossier and stable docs. Before `git rm -r <plan-dir>`, grep stable docs and sibling dossiers for links into the plan dir; promote any cited results file up to `docs/src/planning/<slug>-results.md` (sibling of `-design.md`/`-research.md`) and rewrite the references in the same commit. Cheaper to restore proactively than to chase broken links after deletion.
- 2026-05-27: `cd` inside the Bash tool persists the cwd between calls under nu shell, so a follow-up `git status docs/book` or `grep -rn ... docs/book/` after `cd docs && mdbook build` silently resolves against `docs/docs/book/` and reports "No such file or directory" / "nothing to commit". Use absolute paths (or `git -C <abs>`) for validation greps after any `cd`, otherwise the final stale-reference check is a false negative.
- 2026-05-27: When deleting a whole planning tree, search non-book fixtures and diagnostic scripts too; generated verdict mappings often point at old plan phase files and need stable docs anchors before the plan directory can disappear cleanly.

- 2026-05-27: When the same-session caller already moved durable knowledge into `AGENTS.md` and a memory file before clean-shipped retirement, step 4 is a no-op verify (grep AGENTS.md for the schema sections, ls the memory file). Skip rewriting; just confirm. Avoids duplicating durable content into both AGENTS.md and a stable docs page that does not exist for this repo (canix has no mdBook `docs/src/` tree).
- 2026-05-27: When the plan-set's own final phase was the docs-rollup phase (Phase N: rewrite commands.md / write migration page / append CHANGELOG / bump Cargo.toml), step 4 is again a no-op verify in clean-shipped mode — the predecessor execution already migrated everything. Spend the time on a 4-grep audit instead (sync flag table count in commands.md, line count of the new migration page, count of version-anchor matches in option-b.md and CHANGELOG.md) to prove the rollup actually landed before deleting the plan files.
- 2026-05-28: A "Document plan" commit landing as HEAD with the plan-set's own files modified or with an unresolved-findings untracked doc in `docs/src/planning/` is a strong signal the plan is mid-execution, not retirable. Cheap triage: HEAD commit subject + `git status` + `grep -c '^- \[x\]' <phase>.md` across phases. If any acceptance checkboxes are unchecked AND there are uncommitted edits to files the phase touches, bail out of `general` mode without running deeper inventory — the plan should stay published.

### 2026-05-28 — Skillnet parsing chokes on retired-row markers in phase tables

When a multi-phase plan retires a phase mid-stream (e.g. phase 06 retired and replaced by phase 08), do **not** keep a `| 06 | — (retired) | …` row in the README's phase table — skillnet's `calibration init` parser reads the File column as a filesystem path and fails on the em-dash. Drop the row entirely; document the gap in a one-line note above the table instead. The numbering gap is harmless once skillnet can complete its init.

- 2026-05-28: If the requested planning tree is already gone, still search stable docs and bookkeeping for plan-era phrases such as `Phase N` or `this phase`; a no-op deletion can still need cleanup so user-facing docs read as current product behavior.
- 2026-05-29: In clean-shipped mode, a plan whose own final phase migrated a *new* stable page (e.g. `docs/src/migration/<topic>.md`) needs that page **kept** — it is durable product knowledge, not scaffolding. Prune only the `Plan:`/phase nav block from `SUMMARY.md`; leave the migration entry (here `migration/agents-canonical.md`, line 12) untouched. Confirm post-prune with `ls <page>` + `grep <page> SUMMARY.md` so the rebuild keeps it.
- 2026-05-29: Rebuilding mdBook after `rm -rf docs/src/planning/<slug>` renames the content-addressed `searchindex-*.js`/`toc-*.js` (old hash deleted, new hash added in `git status`). Never grep stale refs by filename — grep file *content* across `docs/src` and `docs/book` for the slug and the human plan title; the renamed index is expected churn, not a leftover.
- 2026-05-29: When a plan's only durable migratable claim is an install/endpoint URL contingent on an external artifact (custom domain, signed apt tree, Pages origin), that claim is NOT foldable while the artifact is verifiably absent — folding it ships a dead install instruction to users. Gate on a live probe before treating any URL as durable: `host <domain>` (DNS) plus `curl -sS -o /dev/null -w '%{http_code}'` against both the path AND the proxied origin behind it. NXDOMAIN / `000` / `404` ⇒ keep the whole plan in planning, fold nothing, edit no repo files. Re-invoking the skill does not change a blocked verdict: re-run the exact endpoint probes, report fresh codes, and stop. This is the converse of the 2026-05-25 "fold *verified* durable guidance" lesson — the verification gate is mandatory, not optional.
- 2026-05-29: In clean-shipped mode, when a plan's durable knowledge is *type-system-enforced* (newtypes that turn the old loose API into a compile error, e.g. removing `Deref<str>` from a `GameId`) plus rustdoc'd on the type and captured in a thorough landing commit, step 4 migration is a no-op verify — the knowledge cannot be lost. Do NOT fold it into a contributor doc (`CONTRIBUTING.md` etc.) that currently has *uncommitted concurrent edits* from a parallel session — that risks clobbering in-flight work. Instead cite the provenance commit hash in the retirement commit message so the record points at the implementation; removing the plan docs then loses nothing durable. Check `git status` of the candidate target before editing it.
- 2026-05-29: In general mode, a mixed planning section can contain both retirable shipped plans and blocked active plans. Retire only the completed subtrees, keep blocked plans published, and repair active-plan references to point at stable docs before deleting the completed subtree; otherwise mdBook keeps broken cross-plan links even though the active plan itself remains valid.
- 2026-05-30: A plan's `.calibration.json` can lag behind the repository when follow-up fixes shipped in later commits or releases. Treat calibration outcomes as a lead, then re-verify retirement against current tags, changelog entries, stable docs, and passing tests before deciding whether the plan is still active.
- 2026-05-31: Final retirement verification must re-run the top-level planning-directory inventory, not rely on an older audit's list. Later active plan sets can make a strict "only this directory remains" assertion false even when the originally superseded plan sets are gone and recoverable from git history.
- 2026-06-01: Completed phase docs may be published from secondary mdBook trees or referenced by app-visible copy, not only `docs/src/planning`. Inventory every `SUMMARY.md` and grep for the retired title/slug across stable docs and source before deletion; fold durable token/workflow guidance into stable architecture or development pages first.
- 2026-06-01: When retiring nearly all of an mdBook planning tree but keeping one current plan set, update the book introduction and the retained plan README too. They often carry prose links to the old planning overview or prior research dossiers that `SUMMARY.md` validation will not catch until the deleted files are gone.
- 2026-06-02: In clean-shipped mode the surrounding mdBook tree may already be broken by a *concurrent, unrelated* plan retirement the user is mid-doing (sibling planning files deleted but still listed in `SUMMARY.md`). `mdbook build` then fails on that earlier section before it ever reaches yours — this is NOT your retirement's failure and the sibling's broken nav is the user's in-flight work, not yours to fix. Validate your own retirement with a content grep for the retired slug + human title across `docs/src/` (expect zero hits) plus `git diff docs/src/SUMMARY.md` to prove your edits touched only your section; don't chase a green full-book build you don't control.
- 2026-06-02: A plan set authored in-session but whose implementation was *already committed before the plan existed* (verify finds 5/7 phases satisfied by a pre-existing commit, the rest by later commits) is still a legitimate clean-shipped retirement — but the durable knowledge worth folding is the cross-cutting *invariant* the surfaces encode (here: a fail-closed, server-side dataset-license gate that must never be confused with the per-record RightsPolicy badge; workspace-only scoping for tables lacking a visibility column; a materialized view that needs manual REFRESH after ingest), not the per-surface build steps the code already embodies. Fold the invariants into one architecture topic page; delete the phase mechanics.
- 2026-06-02: In-session plan sets are not always untracked (cf. 2026-05-26) — a session can *commit* the phase docs, so `git ls-files <plan-dir>` returns all of them and clean-shipped removal is a straight `git rm -rf <plan-dir>` (the `-f` still matters: it covers the `.calibration.json` that the immediately-preceding `skillnet calibration verify` just modified). Always check tracking state first; both outcomes are common. Validation caveat: filtering `git diff SUMMARY.md` through `grep -v '^[-+][-+]'` to drop `---`/`+++` headers *also hides removed list entries* (a deleted `- [Overview](...)` renders as `-- [Overview](...)`), so the filtered diff looks like it dropped only the heading. Don't eyeball the filtered diff to prove a surgical nav prune — grep the slug + human title across `docs/src` for the real zero-hit proof.

- 2026-06-03: When the invocation is "retire … **and fill gaps in order to auto-retire**" paired with a `multi-phase-plan-*` flavour, the correct deliverable is usually NOT an immediate retirement — it is a *gap-filling plan* that sets up the later `verify` → clean-shipped retirement. Run progress review first: a plan that looks shipped can have an invisible tail (here, `postgres-migration`'s server side was fully migrated but its *client-facing* Leptos `#[server]` fns were still `todo!("phase 03")` stubs that panic at runtime — and its own Phase-03 acceptance grepped only `crates/server/src/`, so the narrow criterion passed while the gap lived in `crates/client/src/api.rs`). Retiring on the strength of a too-narrow acceptance grep would have shipped a "done" badge over a panicking app. Lesson: re-derive completion from runtime behavior (does every page render?), not just the plan's own grep; when gaps exist, produce the plan that fills them and document the auto-retire trigger in the new plan's README instead of deleting the partial plan now.
- 2026-06-03: A `todo!("phase N")` marker naming another plan's phase is a cross-plan gap pointer. Grep `todo!\(`/`unimplemented!\(` across *both* `crates/server` and `crates/client` (and any WASM/client crate) when auditing a migration's completeness — the migration's tail often lands in a different crate than the one the phase doc's acceptance criterion greps, so the criterion can read green while the feature panics.
- 2026-06-03: For a **reconciler-tenant** plan set (new crate + NixOS module following an established in-repo tenant pattern, e.g. `*-provision`), step 4 is a no-op verify: the build phase already mandated the durable contract into the crate's own `README.md` (API verbs, business/error codes, security guardrails like write-403-hard-fail and derive-scopes-from-`/routes`, the token/secret model) and the architecture tenant-taxonomy table row is the second durable anchor. Confirm by grepping the crate README for each guardrail + the architecture row for the tenant slug; do NOT author a new stable-docs page. Such plan sets live at `docs/planning/<slug>/` as a *sibling* of the mdBook `docs/src/` tree, so there is no `SUMMARY.md` nav entry to prune — but still content-grep `docs/src/` for the slug + human title (zero hits expected, since planning was never published).
- 2026-06-03: In clean-shipped mode the repo index/worktree may already carry a **concurrent, unrelated** session's staged + unstaged edits (seen here: a `docs/rfcs/ → docs/src/rfcs/` RFC move plus `LICENSING.md`/`REUSE.toml`/`licensing.md` edits, none touched by the retirement). `git rm -rf <plan-dir>` adds your deletions to that *shared* index, so a `git commit` would bundle the other session's staged work with your retirement. Do NOT commit in the skill — stage the plan-dir deletion, prove via `git status --short` that the foreign paths do not intersect `<plan-dir>`, report the foreign staged/unstaged paths, and leave committing to the user.
- 2026-06-03: When retiring predecessor plan directories while a successor plan remains published, the successor's own phase docs may still contain links back to the deleted directories. Rewrite those as stable-doc or retired-history references before the mdBook rebuild; otherwise the source tree can be nav-clean but still publish stale broken links from the retained plan.
- 2026-06-03: When the shipped plan's topic already has a dedicated stable architecture page that documents the *engine/library* side (e.g. `architecture/mediated-access-v2.md` for a closure-only capture model), step 4 is to **extend that page in place** with the *consumer/game-side adoption rules* (the invariants new code must follow: the API pattern, the atomicity rule, the "previously-silent sites now record" gotcha) — not author a new page. A strong signal for exactly what the plan resolved: the existing page's own `## Open questions` section. Convert it to `## Resolved decisions` and answer it from the shipped state (here: "switch `try_modify` to engine deposit?" → resolved, clone-based API deleted). Cheaper and more discoverable than a parallel page.
- 2026-06-03: Commit history can advance *during* the skill run — a concurrent process (or the user) may commit both the implementation and the in-session plan docs mid-session. Re-derive tracking state with `git ls-files <plan-dir>` + `git log --oneline` right before step 5; do not trust an early-session "untracked" read. If now-tracked, it's `git rm -rf` (the `-f` covers the `.calibration.json` the preceding `skillnet calibration verify` just modified), and `git status --short` may show almost nothing under the dir even though 18 files are tracked.
- 2026-06-03: A retired plan's *predecessor* plan (the one whose phase it re-decomposed) keeps forward links into the retired set's README — these break on deletion. Repoint them to the stable architecture page with a one-line "shipped (date) — retired" note rather than leaving a dead `../<retired-slug>/README.md` link; the stale-ref grep across `docs/src` catches them only if you search the slug, not just the deleted paths.
- 2026-06-03: A `verify`-marked-shipped phase whose acceptance included a docs/memory rollup sub-item ("update project_X memory / architecture page to describe the new path") can pass verification on the strength of a *separate* evidence artifact (a `docs/src/reference/<topic>-verify.md` run log) while the rollup sub-item silently never ran. In clean-shipped step 4, do NOT treat "the plan's final phase was a docs phase ⇒ migration already happened" as given — grep the *named* durable home (the specific memory file, AGENTS.md section, or architecture page) for the actual durable facts (crate/API ownership, the fail-closed invariant, the host-config knobs). If absent, fold them before deleting the plan; the per-phase verify verdict is not proof the migration sub-step landed.
- 2026-06-03: A clean-shipped retirement can arrive via repeated `verify` invocations where the *first* verify(s) honestly found 0/N phases done and only a later one finds N/N — because parallel sessions executed AND committed every phase (and the in-session plan docs themselves) between invocations. Don't anchor on an earlier turn's "not-started" read; re-probe acceptance from scratch each verify. The trust-maker for the shipped verdict was re-running the actual reproducible gate (the `netns internet-1v1-forced-relay.sh` smoke to `GAME OVER` + the un-ignored test target), NOT trusting the investigation doc's pasted PASS evidence. When the durable home is an *investigation* doc (`docs/src/investigations/<slug>.md`) the executing session wrote but never added to nav, surface it in `SUMMARY.md`'s Investigations section as you prune the Plan section — don't author a new page. And the generated `docs/book` may have zero hits for a same-session plan slug (the book was never rebuilt with it published), so no book rebuild is owed by your retirement even when `docs/book` is tracked — confirm with `grep -rl <slug> docs/book/`.
- 2026-06-03: Gate retirement on a genuinely-green *reproducible* check, not on "the phase docs exist" or a static audit. A `verify` can come back `shipped` on every acceptance criterion yet hide a real failure that only a first real `nix flake check` surfaces — here the whole test harness shared a broken `test_http_client()` (`reqwest 0.13` `tls_certs_only(empty())` disables system roots, so `.build()` errors "No CA certificates were loaded from the system" in the CA-less sandbox; fix is `tls_danger_accept_invalid_certs(true)`, NOT a flake `cacert`, which the disabled-roots path ignores). The predecessors' earlier "nix flake check green" claim had been a static audit, never a real run, so the latent harness bug rode along. Rule: when a verify needed an out-of-band repair, do not retire until the repair is in the tree and the gate re-runs green from scratch. A "fill-gaps-to-auto-retire" arc then retires *all* plans in the cascade (the two predecessors whose tails were absorbed + the gap-filler itself), predecessors mid-execution and the gap-filler last, each only behind the green gate.
- 2026-06-03: When a retirement phase has explicit deferrals, run the stale-path grep in two modes: strict for actually deleted plan dirs, and annotated for deferred dirs that remain on disk. Journal entries should record retired dirs by bare slug rather than `docs/planning/<slug>` paths so the no-dangling-link grep does not flag the audit trail itself.
- 2026-06-04: When consolidating several plan directories into one replacement under the same planning tree, do not leave phase-file references like `../old-plan/README.md` after deleting the old dirs. Keep old slugs only in the new README's coverage/retirement report and make stale-reference greps exclude that report explicitly.
- 2026-06-04: When retiring an entire `docs/src/planning` tree with both published and unlinked plans, retire the published nav first but audit the unlinked siblings too; if a sibling shipped durable tooling, mirror its runbook into an existing stable mdBook page before deleting the whole directory.
- 2026-06-04: A final cleanup phase can legitimately delete predecessor planning residue while the successor plan remains published. If `multi-phase-plan verify` is partial because external/operator phases still lack reproducible evidence, write the exact green local commands and external producers into the successor plan's verification note, but do not invoke `clean-shipped`; old slugs in that active coverage report are intentional until the external gates land.
- 2026-06-05: If an unlinked `docs/planning` plan has repo-local phases shipped but live-host/operator phases still lack evidence, keep the plan files and fold only the verified module/API invariants into stable docs. Do not delete the plan just because it is absent from `SUMMARY.md`; absence from published nav is not completion evidence.
- 2026-06-05: When the cleanup goal is specifically to eliminate `docs/planning`, an active-but-unshipped plan can be moved to a non-docs operational home such as `upstreaming/<slug>/`. Patch hard-coded old paths and assert `test ! -e docs/planning`; a nav-only cleanup is insufficient.
- 2026-06-05: In a mixed active plan set, a single completed phase can be retired from published navigation while the parent plan remains visible. Fold the phase's durable invariant into stable docs, delete only that phase file, and rewrite the parent README so remaining phase tables do not link to the deleted file.
- 2026-06-06: A final cleanup phase can satisfy its retirement criterion without deleting any directories when the remaining plans are explicitly active/deferred. Record "no additional planning directories were retired" in the journal, preserve the active dirs, and validate docs; forcing deletion would lose unresolved operator evidence.
- 2026-06-06: An explicitly abandoned external phase can be retired with the rest of a plan only after the non-execution decision is preserved in stable operations history. Update and `jq` the calibration sidecar before deleting the plan directory, then report that the sidecar was verified pre-deletion rather than pretending the post-retirement path still exists.
- 2026-06-06: In clean-shipped mode for an untracked in-session plan under a repo with no mdBook stable docs, fold durable behavior into `README.md` before `rm -rf` deletion. Verify `git ls-files <plan-dir>` is empty first, and keep the companion research dossier only if it remains intentionally useful as architecture context.
- 2026-06-06: When the caller explicitly defers a single phase inside an otherwise retired `docs/src/planning` tree, rewrite the deferred phase into a standalone follow-up before deleting its parent README. Preserve exact external producers and validation commands in the deferred page and stable runbook, then publish only that page from `SUMMARY.md`.
- 2026-06-06: When retiring stale benchmark datasets, audit generated figure-input manifests as data too. A manifest with `exists=true` for a deleted Parquet file is stale evidence and should be regenerated from the retained real bundle or removed with the raw dataset.
